✅ **Issue fixed** – integrations that fail during setup are no longer treated as “enabled”.

### 🔍 What was wrong

In `sentry_sdk.integrations.setup_integrations()`:

* Default (auto‑enabling) integrations that raised `DidNotEnable`
  were still:
  * added to `_installed_integrations`
  * left in the dictionary returned by `setup_integrations()`

This meant a user inspecting `client.integrations` would see a
“working” entry for an integration that never actually hooked anything.
Repeated calls also stopped re‑trying the setup.

### 🛠 What I changed

Modifications in __init__.py:

1. **Skip installing** default integrations that raise `DidNotEnable`.
2. **Prevent** them from being added to `_installed_integrations`.
3. **Remove** them from the returned `integrations` dictionary.
4. Adjust logging so only truly enabled integrations are reported.

Explicitly‑requested integrations still propagate the exception as before.

A helper set `skipped_defaults` keeps track of defaults that failed and
ensures they’re purged before the final `return`.
